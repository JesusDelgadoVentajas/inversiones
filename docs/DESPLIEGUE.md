## Condiciones previas

1. El propietario comprueba en su cuenta real Workers Free, D1 Free, Access gratuito, recuperación y facturación. Actualizar [COSTES](COSTES.md); no elegir un producto de pago para completar la guía.
2. Crear una política de Access para **los dos correos exactos autorizados** por el propietario, conservados de forma privada. El propietario completó el [alta de Zero Trust](https://developers.cloudflare.com/cloudflare-one/setup/) en Free y confirmó importe cero, sin cobro; conservar ese plan. La protección con **All traffic** debe cubrir todo el Worker, rutas, `workers.dev` y previews; no añadir datos reales hasta probarla. Una política solo por hostname no cubre automáticamente otras rutas del Worker. Evitar `Everyone` o `Bypass`.
3. Comprobar que staging y producción reciben audiencias Access distintas. Obtener de la cuenta `ACCESS_TEAM_DOMAIN`, los AUD reales y `ACCESS_ALLOWED_EMAILS`; no escribir valores en Git ni en un argumento de shell. Preparar el método seguro local/secretos de Workers.

## Orden técnico y progreso

1. **Hecho:** dos D1 remotas independientes y bindings reales en `env.staging.d1_databases` y `env.production.d1_databases` de `app/wrangler.jsonc`. Crear estas bases privadas con la sesión autorizada no depende de publicar un Worker ni de Access. Revisar límites gratuitos antes de crear recursos. Si se clona para otra cuenta, no recrear ni migrar a ciegas: comprobar titular y sustituir ambos UUID por sus bases reales.
2. **Hecho:** cinco migraciones en local, staging y producción; nueve tablas vacías y claves foráneas comprobadas remotamente. `npm run check` verifica contratos/configuración/build; la instalación limpia ya se había probado. Las siguientes migraciones se ensayarán primero en local y staging antes de producción. Desde `app/`, seleccionar explícitamente `--config wrangler.jsonc` y `--env` al usar Wrangler remoto para evitar un artefacto seleccionado anteriormente por el plugin Vite. Nunca confundir crear una base con repetir una migración de una base existente.
3. Introducir `ACCESS_TEAM_DOMAIN`, `ACCESS_AUD` y `ACCESS_ALLOWED_EMAILS` como [secretos de Worker](https://developers.cloudflare.com/workers/configuration/secrets/) **por entorno**. `ACCESS_ALLOWED_EMAILS` ya se envió y comprobó en staging; faltan dominio/AUD allí y los tres secretos en producción. La lista es una cadena JSON de correos válidos; la plantilla local solo muestra ejemplos ficticios. El AUD de staging debe corresponder a su aplicación y el de producción a la suya. Usar flujo interactivo, `wrangler secret bulk` desde un archivo privado 0600 o `deploy --secrets-file` con ese archivo. No copiar valores a documentación, registros ni frontend. `ACCESS_OWNER_EMAIL` ya no configura el guard; no utilizarlo como alternativa.
4. **Hecho para staging:** armazón inerte publicado con destino/flags verificados y URL de versión desactivadas; alta Zero Trust Free confirmada por el propietario. Falta protegerlo: abrir **Workers & Pages → inversiones-staging → Access**, seleccionar **Protect this Worker behind Access → All traffic**. Si el diálogo solo ofrece cuenta/dominio, usar la cuenta como protección provisional y editar la aplicación en **Zero Trust → Access → Applications**: dejar una única política `Allow` con `Include → Emails` y los dos correos exactos autorizados. Se admite cualquiera de los dos; no añadirlos como dos requisitos obligatorios ni conservar reglas de dominio, cuenta, `Everyone` o `Bypass` que amplíen acceso. [Protección de Worker](https://developers.cloudflare.com/workers/configuration/cloudflare-access/#protect-one-worker), [reglas de Access](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/).
   Añadir **One-time PIN** como método de inicio de sesión en **Zero Trust → Integrations → Identity providers → Add new identity provider**, y habilitarlo para esta aplicación. En organizaciones nuevas no se añade automáticamente; permite verificar cualquiera de los dos buzones sin exigir dos cuentas Cloudflare. El PIN se introduce solo en la página de Cloudflare. [Configuración oficial](https://developers.cloudflare.com/cloudflare-one/integrations/identity-providers/one-time-pin/). No usar el método PIN como regla `Include` adicional: ampliaría el acceso a cualquier correo.
5. **Carga móvil del armazón confirmada.** Después de configurar secretos y Access, probar sesión autorizada y navegador sin sesión, `workers.dev` y cualquier dirección alternativa. Revisar página estática, salud y `/api/v1/capabilities`; la API debe denegar token ausente/ajeno y conservar `APP_READY=false`. Repetir el inicio de sesión en el móvil fuera de la red local. Medir JWT frío/caliente, CPU, errores y cuotas Free; documentar evidencias saneadas. Si falla protección/configuración, no habilitar proveedores.
6. Solo tras G-ACCESO y G-DATOS, añadir secretos de fuentes aprobadas por entorno, límites contractuales y adaptadores; activar datos con un cambio revisado y nuevo despliegue. No basta cambiar una variable en un artefacto antiguo: compilar para el entorno correcto.
